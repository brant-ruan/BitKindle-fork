# Implementation design

This page describes internal design details useful when reading the source. Source paths below are relative to `src/bootstrap-c99/`.

## Initializer parser state

The compiler saves and restores state while parsing nested initializers. A checkpoint frame has 58 slots: declaration and designated-initializer flags occupy slots 54/55, while wide-literal and concatenated-string flags have separate slots 56/57. Allocation, saving, and restoration must use the same layout so that inner parsing does not corrupt outer state.

Related tests call the compiler's actual checkpoint functions and cover nested frames and combinations of outer flags. Aggregate initializer regression remains part of the full test suite. This is an internal layout, not a public interface.

## Public headers and runtime

`include/` provides public headers. The C89 runtime selects mathematical, numeric-conversion, and locale-layout policies through `runtime/runtime-c89.c`. The compiler setting `C1_RUNTIME=c89` only selects runtime export policy in object mode; ordinary applications should leave it unset.

Public function prototypes use implementation-reserved parameter names to prevent caller macros from rewriting declarations. The stdio FILE/fpos_t members and additional C89 lconv members use corresponding reserved names. Runtime compilation uses the same mappings to preserve layout consistency. C99 locale headers retain their standard member names.

`namespace/` tests public headers, runtime symbols, macro collisions, and language-mode conventions. Source-inclusion tests in the base bootstrap stage have their own header configuration and cannot replace public-interface tests.

## Bootstrap and full mathematical runtime

Generation zero of the final compiler uses `runtime/bootstrap-runtime.c`. The next two generations use the full `runtime/runtime.c`, including complex arithmetic, type-generic mathematics, and the corresponding real mathematical interfaces. The C89 runtime excludes interfaces introduced only in C99. See [BOOTSTRAP.md](../BOOTSTRAP.md) for the complete build dependencies.

`complex/SUITES.json` lists mathematical and complex test suites and their completion markers. Mathematical tests may use PowerShell to generate C reference-data text, but binaries for those C files are still produced by the custom compiler and linker. Algorithms, independent reference methods, and numerical boundaries are described in the [algorithm documentation](README.md).

## Locating validation

Language rules and mode differences are primarily tested in `diagnostics/`, `namespace/`, and `features/`; base regression tests are in `base/tests/`. Independent audits check diagnostics, rejection of invalid input, execution results, and equality of artifacts from both generations. Some mathematical fixtures contain x64 MXCSR operations generated by the custom compiler to test all four rounding modes.

Test counts and build results must be taken from actual run logs. Passing selected cases does not prove correctness for all inputs or extend the project's C99 or optional floating-point annex support claims.
