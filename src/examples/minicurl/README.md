# minicurl: fetch web pages with the custom C compiler

A Windows x64 command-line GET client using system WinHTTP for HTTP/HTTPS. It supports redirects, query strings, chunked responses, response bodies on stdout, raw-byte file output with `-o`, and explicit HTTP proxies. Source: `minicurl.c`; output: `minicurl.exe` in this directory.

## Build and run

First build the toolchain with `build-all.ps1` in any mode from the release root; see [Build instructions](../../../README.md#quick-start). `-All` already builds this example, and `-Full` also runs its local HTTP tests. In those cases, skip compilation below.

Run these commands in **Windows PowerShell 5.1** from this example directory:

```powershell
# Compile the example with the built custom toolchain.
./build.ps1
if (!$?) { throw 'Build failed' }

# Write the response body to the terminal; HTTP status goes to stderr.
./minicurl.exe https://example.com/

# Save the page with -o to avoid PowerShell 5.1 text-redirection transcoding.
./minicurl.exe -o example.html https://example.com/
$LASTEXITCODE

# Quote arguments containing shell metacharacters such as &.
./minicurl.exe -o result.html 'https://example.com/?a=1&b=2'

# If using an HTTP proxy, supply its actual host and port without http://.
./minicurl.exe --proxy 127.0.0.1:8080 -o example.html https://example.com/

./minicurl.exe --help
```

`build.ps1` defaults to `../../bootstrap-c99/build-from-seed`, relative to the script directory. You can also use the staged toolchain:

```powershell
./build.ps1 -BuildDirectory '../../../work/walkthrough'
if (!$?) { throw 'Build failed' }
```

The selected directory must contain `host/c1-stage2.exe` and `link-stage2.exe`. The script builds its own runtime. Selecting custom tools does not change the example's output location.

## Build process

1. Set `C1_STANDARD=c89`, `C1_OUTPUT=object`, and `C1_INCLUDE` to the project's standard-header directories.
2. The custom `host/c1-stage2.exe` reads `minicurl.c` from stdin and writes `build/minicurl.c1o` to stdout. The project's `Compile` function transfers those bytes unchanged.
3. A small runtime wrapper defines `C1_MAIN_ARGS=1` and includes `runtime-c89.c`. The same compiler produces `build/runtime.c1o` supporting `main(int, char **)`.
4. The custom `link-stage2.exe` links the objects into PE with entry `__c1_start`. `--import symbol DLL export` specifies Windows imports, for example `--import WinHttpOpen WINHTTP.dll WinHttpOpen`.

Every object and EXE is generated by custom tools. The program explicitly imports KERNEL32.dll and WINHTTP.dll without Windows SDK headers or `.lib` import libraries.

`minicurl.c` declares the Windows ABI it needs and checks DWORD, WCHAR, pointer, and URL-structure layouts at runtime.

`build/provenance.json` records SHA256 hashes of the compiler, linker, and generated program. Root `clean-all.ps1` removes this example's `build/` and `minicurl.exe`, but not `example.html` or `result.html` saved by the sample commands. Tool interfaces are in [USAGE.md](../../../USAGE.md).

## Tests

```powershell
# Local HTTP tests; the server binds only to a random port on 127.0.0.1.
./test.ps1

# Add public HTTPS tests; HTTPS_PROXY, if set, is explicitly passed as an HTTP proxy.
./test.ps1 -Internet
```

Build the example first. The default has 12 cases: help, argument errors, invalid protocol, embedded-credential rejection, HTTP, redirects, chunked transfer, query/fragment handling, 404, binary file output, binary stdout, and output failure. Bodies are checked byte for byte. Binary cases use 51,200 bytes covering all 256 values across multiple read buffers.

Each case has a 60-second timeout. After all pass, results are written to `build/tests/RESULTS.txt`; individual stdout and diagnostics are stored beside it. Current script errors determine failure; an old results file is not evidence of a new pass. `-Internet` additionally downloads an HTTPS page to `build/tests/example.html` and checks its content.

Optional HTTPS tests need working networking and system certificates. If `HTTPS_PROXY` is set, it must be `http://HOST:PORT` without credentials. A proxy is not required. PowerShell/.NET supplies only the test server and data checks.

## Behavior and scope

- Exit codes: 0 success; 2 argument/URL error; 3 network/TLS error; 4 output error; 22 for HTTP status >= 400. HTTP error bodies are still emitted.
- Windows automatic proxy configuration is used by default; `--proxy HOST:PORT` selects an HTTP proxy. The program does not automatically read curl proxy environment variables.
- Certificate validation and redirects use WinHTTP defaults. There are no options to bypass certificate checks or change redirect policy.
- Use ASCII/punycode hostnames and percent-encoded UTF-8 for non-ASCII paths. URLs are limited to 8,189 bytes; embedded usernames/passwords are unsupported.
- Each network phase has a 15-second timeout, not a total download deadline. Bodies are streamed instead of held entirely in memory.
- `-o` overwrites the destination; interrupted or failed downloads may leave partial data. Stdout receives raw response bytes, whose display depends on terminal encoding.
- This GET example does not implement POST, cookie management, custom headers, decompression, complete curl options, or webpage JavaScript execution.
